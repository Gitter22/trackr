# Trcker — Critical Analysis

This is an honest look at where the current schema and architecture can break: slow queries, data getting out of sync, scale limits and security gaps. Each item says how bad it is and what we do about it.

**Severity:** 🔴 must fix in Phase D · 🟠 fix in Phase D if cheap, otherwise soon after · 🟢 later, when data grows

---

## 1. N+1 query risks in GraphQL resolvers

An N+1 happens when a list of N items runs one more query per item. The board is the worst case: 6 columns × 50 cards, each card needing its assignees, labels and comment count.

| Field                                                                     | Risk                                                               | Fix                                                                                                                                                                  |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Task.assignees`, `Task.labels`                                           | 🔴 One query per card                                              | DataLoader keyed by `taskId` → one `WHERE task_id IN (...)`                                                                                                          |
| `Task.status`, `Task.createdBy`, `Task.project`                           | 🔴 One query per card                                              | `statusById`, `userById` and `projectById` loaders                                                                                                                   |
| `Task.commentCount`                                                       | 🔴 One `count(*)` per card                                         | A loader running one `GROUP BY task_id`                                                                                                                              |
| `Comment.author`, `Comment.replies`, `TaskActivity.actor`                 | 🔴 One query per comment or activity row                           | `userById` loader, plus a `repliesByParentId` loader                                                                                                                 |
| `Project.members`, `statuses`, `labels`, `taskCount` on the projects list | 🟠 One query per project                                           | Loaders keyed by `projectId`                                                                                                                                         |
| **Permission checks** ("is the viewer a member of this task's project?")  | 🔴 Hidden N+1: every resolver checks again                         | A `membership` loader keyed by `projectId`. It returns one cached answer for each request.                                                                           |
| `TaskConnection.totalCount` on each board column                          | 🟠 One `count(*)` per column                                       | A loader that counts all requested columns in one `GROUP BY status_id`. Only compute it when the client asks for it.                                                 |
| **Paged lists inside a loader** (first page of each column)               | 🟠 DataLoader can't batch "first 50 where status = X"              | Accept one query per column (about 6 per board). Or load every column's first page in one query with `ROW_NUMBER() OVER (PARTITION BY status_id ORDER BY rank, id)`. |
| Deep nesting (`tasks → comments → replies → author → …`)                  | 🟠 Loaders batch each level, but a hostile query can still be huge | Limit query depth (for example 8) and query cost, and cap `first` at 100                                                                                             |

Rules:

- Loaders are created **fresh for each request**, so cached data never leaks between users or tenants.
- A test will count SQL statements for a full board query and fail if the count grows with the number of cards.

## 2. Data consistency challenges

| Area                                                                     | What can go wrong                                                                                                                              | Approach                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fractional rank**                                                      | Repeated drops into the same gap halve it every time. After about 50 halvings, two floats are equal.                                           | 🔴 When the gap drops below `1e-6`, renumber the whole column (1000, 2000, …) in one transaction. Take a Postgres advisory lock on `statusId` so two renumbers can't overlap. Equal ranks never break pagination, because `id` breaks the tie. |
| **Concurrent moves**                                                     | Two users drop different cards into the same gap and both get the same rank                                                                    | 🟢 Harmless: `id` decides the order. The renumbering above cleans it up over time.                                                                                                                                                             |
| **Concurrent edits**                                                     | Two people edit the same task. The last save wins silently.                                                                                    | 🟠 The history shows both changes. Later, `updateTask` can take an `expectedUpdatedAt` and reject a save based on stale data.                                                                                                                  |
| **Task numbers**                                                         | Two creates read the same `taskSeq`                                                                                                            | 🔴 Use `UPDATE projects SET task_seq = task_seq + 1 RETURNING task_seq` inside the create transaction. It is atomic thanks to the row lock. `@@unique([projectId, number])` is the backstop.                                                   |
| **Changing a status's category** (e.g. "Done" from STARTED to COMPLETED) | Every task in it changes meaning, and `completedAt` must be set or cleared on all of them                                                      | 🔴 Do it in one transaction: update the status, then bulk-update `completedAt` for its tasks. Write one history entry per task, or a single bulk entry.                                                                                        |
| **Deleting a status**                                                    | Its tasks would be left without a status                                                                                                       | 🔴 Status delete requires `moveTasksToStatusId` from the same project, and moves the tasks in the same transaction. Block deleting the last status.                                                                                            |
| **Soft deletes**                                                         | One forgotten `deletedAt IS NULL` shows deleted tasks or counts them                                                                           | 🔴 A single Prisma client extension or query helper adds the filter by default. It gets a test.                                                                                                                                                |
| **Project limit**                                                        | Two "create project" requests both pass a `count < limit` check                                                                                | 🟠 Check and insert in one transaction while holding a lock on the `projectLimit` setting row (`SELECT … FOR UPDATE`)                                                                                                                          |
| **Control DB and tenant DB copies**                                      | The org owner exists in both. Timezone and project limit are copied into `OrgSetting`. An edit in the control panel won't reach the tenant DB. | 🟠 The control panel writes to both in one operation and retries on failure. The tenant DB copy is what the app reads.                                                                                                                         |
| **Org deactivated, cache still says active**                             | Redis caches tenant status for 60s                                                                                                             | 🔴 Delete the Redis key whenever an org's status changes. The 60s TTL is only a safety net.                                                                                                                                                    |
| **Provisioning fails halfway**                                           | The DB exists but migrations failed, so a retry fails on "database exists"                                                                     | 🔴 Every step is safe to re-run: create the role or DB only if missing, and `migrate deploy` is already re-runnable. A "Retry" button re-runs the steps.                                                                                       |
| **Denormalized counters**                                                | Stored counts like `commentCount` or `taskCount` drift if one code path forgets them                                                           | 🟢 We store none today. They are computed through loaders. If we add one, it is updated in the same transaction as the change, and a repair job can rebuild it.                                                                                |
| **Overdue around midnight**                                              | "Today" differs by timezone                                                                                                                    | 🟢 Always use `(now() AT TIME ZONE orgTz)::date`, never the server's clock or the browser's                                                                                                                                                    |

## 3. Scalability at 100x

Assume we grow from about 100 orgs to **about 10,000 orgs**, with the biggest orgs at **about 1M tasks and 10M history rows**.

| Bottleneck                               | Why it breaks                                                                      | Plan                                                                                                                                                      |
| ---------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DB connections**                       | 5 connections × 1,000 active tenants = 5,000. Postgres handles a few hundred well. | 🟠 Put **PgBouncer** (transaction mode) in front of Postgres. Lower the limit to 2 per tenant. Cap the LRU cache size, e.g. 200 clients per API instance. |
| **Thousands of databases on one server** | Startup, backups, autovacuum and monitoring all slow down with 10k DBs             | 🟢 Spread tenants across several Postgres servers. Add `Organization.dbHost` (expand migration) so each tenant can live on any server.                    |
| **PrismaClient per tenant**              | Each client costs memory and a cold start. Many tenants cause cache churn.         | 🟢 Route a tenant to the same API instance (e.g. hash the slug at the load balancer) so its cache stays warm                                              |
| **Running migrations on every tenant**   | 10k DBs one after another takes hours                                              | 🟢 Run N in parallel. Track the version per tenant. The code supports both the old and new schema during rollout (expand, then contract).                 |
| **History table size**                   | `task_activities` grows fastest                                                    | 🔴 Paginate `Task.activity`; it is an unbounded list today. 🟢 Later, partition by month or move old rows to cold storage.                                |
| **Comment thread size**                  | `Task.comments` is unbounded                                                       | 🟠 Paginate it the same way                                                                                                                               |
| **Board summary counts**                 | `count(*)` over 1M rows on every board load                                        | 🟠 Cache the summary in Redis for about 30s for each project and filter. 🟢 Later, keep counts per status, updated when tasks move.                       |
| **Title search**                         | `ILIKE '%x%'` can't use a normal index                                             | 🟢 Use the `pg_trgm` GIN index on `tasks.title`                                                                                                           |
| **Redis**                                | One instance handles the cache and the rate limits                                 | 🟢 Use managed Redis with a replica. If Redis is down, fall back to the control DB for tenant lookup.                                                     |

## 4. Security concerns

| Concern                                    | Risk                                                                                                                | Fix                                                                                                                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Spoofed `X-Tenant-Slug`**                | Nginx strips the header, but if the API port (`:4000`) can be reached directly, a client can send any slug          | 🔴 Keep the API on the Docker network only, not published to the host. Require a shared secret header that only Nginx and the Vite proxy add. The JWT check below is a second guard. |
| **Token used on another tenant**           | A token from `acme` sent to `kiksasa`                                                                               | 🔴 JWT `aud = tenant:<slug>` must equal the request's slug. Cookies set **no `Domain`**, so the browser never sends them to other subdomains.                                        |
| **Wrong IDs (IDOR)**                       | Using a valid ID from a project you can't see                                                                       | 🔴 Every by-ID resolver (`task`, `updateTask`, `deleteComment`, …) loads the item's project and checks membership. Not found and forbidden both return "not found".                  |
| **IDs from another project in a mutation** | `moveTask` with a `statusId` from another project, or `labelIds` or `assigneeIds` that don't belong to this project | 🔴 Check that every referenced ID belongs to the same project. Assignees must be project members. `afterTaskId`/`beforeTaskId` must be in the target column.                         |
| **Default passwords**                      | Every user starts with the same known password (`User@123`)                                                         | 🟠 Add `User.mustChangePassword` and force a change on first login. _(Small schema change, recommended.)_                                                                            |
| **Login brute force**                      | Guessing passwords                                                                                                  | 🟠 A separate rate limit on login for each IP and email, on top of the per-tenant bucket                                                                                             |
| **Unknown subdomain flood**                | Random slugs miss the Redis cache and hit the control DB every time                                                 | 🟠 Cache "not found" for a short time (e.g. 30s), and rate-limit unknown hosts by IP                                                                                                 |
| **`CREATE DATABASE` injection**            | The slug ends up in raw SQL                                                                                         | 🔴 Strict slug regex `^[a-z][a-z0-9-]{2,31}$` plus a reserved-word list. Identifiers are always quoted. The role password is random.                                                 |
| **Powerful provisioning login**            | The API holds Postgres superuser credentials to create databases                                                    | 🟠 Use a dedicated role with `CREATEDB CREATEROLE` only, never the superuser. 🟢 Later, move provisioning into a separate worker.                                                    |
| **Tenant DB passwords**                    | Stored in the control DB                                                                                            | Done: AES-256-GCM encrypted, with the key from env, never returned by any API                                                                                                        |
| **Abusive GraphQL**                        | Huge or deeply nested queries; introspection in prod                                                                | 🔴 Depth and cost limits, `first ≤ 100`, introspection off in production, Yoga's CSRF protection on                                                                                  |
| **XSS in comments and descriptions**       | Users store HTML or JS                                                                                              | 🔴 Render as plain text, or as sanitised markdown                                                                                                                                    |
| **Seeded super admin**                     | `Test@123` is in the spec                                                                                           | 🟠 Fine locally. Production must set it from secrets, and startup refuses the default value when `NODE_ENV=production`.                                                              |

## 5. Missing indexes and denormalization ideas

| Idea                                                                               | Why                                                                                                                                                                                                                           | When                                                               |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **`Task.isClosed` boolean** (true when the category is COMPLETED or CANCELLED)     | Overdue queries join `task_statuses` just to check the category. With this flag, "my overdue tasks" becomes `WHERE is_closed = false AND due_date < today` with no join. It is kept in sync on move and on a category change. | 🟠 _Small schema change, recommended._                             |
| **Partial index** `tasks(due_date) WHERE is_closed = false AND deleted_at IS NULL` | The overdue index then holds only open tasks, a small fraction of all tasks                                                                                                                                                   | 🟠 Raw SQL in a migration (Prisma 6 can't express partial indexes) |
| **Partial board index** `tasks(status_id, rank, id) WHERE deleted_at IS NULL`      | Leaves soft-deleted rows out of the hottest index                                                                                                                                                                             | 🟢 When deletes pile up                                            |
| **`pg_trgm` GIN on `tasks.title`**                                                 | Fast search                                                                                                                                                                                                                   | 🟢                                                                 |
| **`task_activities(actor_id, created_at)`**                                        | "What did this user do?" for audit                                                                                                                                                                                            | 🟢 When we build an audit view                                     |
| **Stored counts by status**                                                        | Summary without `count(*)`                                                                                                                                                                                                    | 🟢 At 100x only                                                    |
| **`Project.shortCode` immutable**                                                  | Task keys (`KIK-12`) are built from it. Renaming it would break links people saved.                                                                                                                                           | 🔴 Block edits in the API (the schema stays as it is)              |
| **`Organization.dbHost`**                                                          | Spreading tenants across servers                                                                                                                                                                                              | 🟢 At 100x                                                         |

Already covered, with no extra index needed:

- `task_assignees(task_id)`, `task_labels(task_id)` and `project_members(project_id)`, by their composite primary keys
- task lookup by key, by `@@unique([projectId, number])`

---

## Summary: what changes before Phase D

**Schema changes recommended now** (small, cheap before any data exists):

1. `Task.isClosed`, plus the partial overdue index in raw SQL
2. `User.mustChangePassword`
3. Paginate `Task.activity` and `Task.comments` in the GraphQL schema

**Built into Phase D:** everything marked 🔴 above. That covers the loaders, renumbering under a lock, the atomic `taskSeq`, status category change and status delete in a transaction, the default soft-delete filter, clearing the Redis key on status change, re-runnable provisioning, the API not exposed plus the shared proxy secret, checking IDs belong to the same project, GraphQL limits, and safe comment rendering.

**Later (🟢):** PgBouncer, spreading tenants across servers, history partitioning, trigram search, stored counters.
